# AI_LOG — отчёт о работе с ИИ

## 1. Инструменты и модели

- **Google Gemini 4 ** (веб-чат) — генерация каркаса: Pydantic-схемы, модели SQLAlchemy, чистые функции расчётов, базовые тесты `pytest`.
- **Claude Sonnet 5.5** (веб-чат Anthropic) — ревью готового кода: приложил PDF с ТЗ и репозиторий, попросил проверить реализацию по каждому пункту ТЗ.
- **PyCharm** — IDE, запуск тестов.

## 2. Ключевые запросы

1. **Расчёт скидки и графика рассрочки без `float` (Gemini):**
   > «Нужно написать чистые функции расчёта 10% скидки по промокоду KVITTO10 и графика рассрочки на 3, 6 или 12 месяцев. Все суммы строго в копейках (`int`), использовать `float` запрещено. Сумма всех платежей графика должна ровно сходиться с итоговой суммой к оплате, а лишние копейки от остатка деления должны распределяться по первым платежам (например, 1990000 на 3 месяца -> [663334, 663333, 663333])».

2. **Валидация входных данных на Pydantic v2 (Gemini):**
   > «Собери схему `PaymentCreate` на Pydantic v2: тарифы `basic`/`standard`/`premium`, методы `card`/`sbp`/`installment`. Если выбран `installment`, обязательно поле `installment_months` (3, 6, 12), для других методов оно должно быть запрещено. Промокод `KVITTO10` регистронезависимый, любой другой код должен вызывать стандартную ошибку валидации FastAPI 422».

3. **Фикстура для тестов с изоляцией БД (Gemini):**
   > «Напиши фикстуру `pytest` для тестирования FastAPI через `TestClient` с использованием in-memory SQLite (`StaticPool`) и подменой зависимости `get_db` через `app.dependency_overrides`, чтобы тесты не затрагивали локальный файл базы данных».

4. **Ревью готового кода по ТЗ (Claude):** приложил PDF с заданием и репозиторий, попросил проверить всё согласно ТЗ. Ответ разобрал по пунктам и исправил найденное (см. раздел 3).

## 3. Где модель ошиблась и как это нашлось

Все четыре проблемы были в коде, который сгенерировала Gemini. Я нашёл их не сразу, а при ревью кода (запрос № 4), после чего исправил и добавил проверки в тесты.
- Тесты затрагивали локальную БД. TestClient запускался через контекстный менеджер и вызывал lifespan, использующий kvitto.db. Для тестов настроена отдельная SQLite in-memory БД, тарифы создаются в фикстуре, TestClient не запускает lifespan.
- Не работал фильтр ?status=. Параметр назывался status_filter; добавлен alias status и тест фильтрации.
- Повторные запросы могли конфликтовать при одновременном создании платежа. Добавлены обработка IntegrityError, откат транзакции и повторный поиск платежа по Idempotency-Key. Тест проверяет последовательный повтор и отсутствие дубля; конкурентный сценарий отдельным тестом не проверен.
- created_at мог возвращаться без часового пояса. В схеме ответа наивный datetime, считанный из SQLite, помечается как UTC; тест проверяет UTC-смещение.
ИИ ускорил реализацию, но его предложения пришлось проверять по ТЗ и исходникам. Особенно важно проверять не только HTTP-код, но и состояние БД и фактические данные в ответе.
